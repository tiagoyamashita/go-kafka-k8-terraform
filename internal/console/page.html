Common Failures

What you see, who decides it, and the situation that produces it. A Demo note in the last column can be forced from the request list.

What you seeWho decidesWhen it happens
A red line in the send pane. Nothing new on the right. Send pane Catch it on the front end is checked. The body is not a JSON object with a UUID id, or it is larger than 64KiB. Kafka is not called.
A green line saying the receiver will dead-letter it. A row under Dead-lettered, and no consumed row. Receiver Catch it on the front end is unchecked. Send a Receiver request, including Receiver: larger than 64KiB. The receiver writes the error to transfers.dlq and does not store it.
MESSAGE_TOO_LARGE under Kafka errors. Kafka Catch it on the front end is unchecked. Send Kafka: message too large. The body is random text, so it stays over 64KiB after compression and transfers.in refuses it. Receiver: larger than 64KiB is only the letter x, which compresses under that limit, so Kafka accepts it and the receiver dead-letters it. With the checkbox checked, the pane stops the large body and Kafka is not called.
UNKNOWN_TOPIC_OR_PARTITION under Kafka errors. Kafka Send Kafka: unknown topic. The produce goes to transfers.missing. Topic auto-create is off, so the broker does not create it. The body is valid, so the checkbox does not stop it.
INVALID_TOPIC_EXCEPTION under Kafka errors. Kafka Send Kafka: invalid topic. The topic name is bad topic, which the broker will not accept.
A dial error for 127.0.0.1:1 under Kafka errors. Kafka client Send Kafka: wrong address. Nothing listens on that port, so the produce fails before a broker sees it.
broker unreachable at 192.0.2.1:9092 under Kafka errors. Kafka client Send Kafka: broker unreachable. That address does not route, so the dial times out. The cluster broker is still up.
ILLEGAL_SASL_STATE under Kafka errors. Kafka Send Kafka: SASL rejected. The listener is plaintext. The client offers SASL, and the broker rejects that request. This cluster has no access-control list that denies a normal client.
A green Sent line. The id never appears under Consumed messages. Receiver The receiver is stopped, or Postgres refused the insert. The record stays on transfers.in. A store error is not dead-lettered.
A green Sent line for an id that is already listed. Still one row. Receiver The same UUID was produced again. The insert is skipped.
The consumed row stays received. Transmitter The transmitter is stopped or not polling. The row is stored, and nothing has tried transfers.out.
The row goes failed, then published. Transmitter or Kafka One publish to transfers.out fails and a later one succeeds. A short broker blip or a single rejected produce. Demo: Fail publish once.
The row stays failed, then becomes dead. The body also shows under Dead-lettered. Transmitter Every publish to transfers.out fails until the attempt cap, five tries about two seconds apart. The topic is missing, access is denied, the record is over the broker limit, or the broker stays down. Demo: Fail until dead. A real sender does not send "fail": "always".
The row stays failed after the attempt cap and does not become dead. Transmitter The cap was reached, and the write to transfers.dlq failed too. It becomes dead only after that write succeeds.
The row is stored and published even though a business field looks wrong. Nobody rejects it The receiver only requires a JSON object with a UUID id. A string amount, or a payload that is not an object, is stored as sent.

Grafana

Metrics and traces for the receiver and the transmitter. Open http://127.0.0.1:30080 after the observability apply, as admin / admin. The Transfers dashboard stays empty until those pods are running. Prometheus scrapes receiver:8080 and transmitter:8080. It does not scrape the console.

QuestionWhereWhat to look at
Did receives stop? Transfers, Receive and publish rate transfer_received_total stays flat while the send pane still says Sent. The receiver is down, or Prometheus cannot scrape it.
Are publishes stuck? Outbox depth, and Errors, retries, and dead letters Depth climbs while rows stay received or failed. transfer_retries_total counts refused publishes. transfer_dlq_total counts dead letters.
Is Postgres or Kafka slow? Persist and publish latency p95 of transfer_persist_duration_seconds and transfer_publish_duration_seconds.
What happened to one message? Explore, Tempo Paste the trace_id from a log line. The spans are transfer.consume, transfer.insert, transfer.publish, and transfer.deadletter.

ELK

Elasticsearch, Logstash, and Kibana are not in this cluster. The receiver and the transmitter write one JSON object per line to stdout. Ship that output with Filebeat or Fluent Bit. Logstash is only needed if you want to change the line before it is indexed. A retry that was saved as failed does not print an error line. Use the Grafana retry counter for those.

QuestionWhereWhat to look at
Where are the logs right now? The process stdout, or kubectl -n transfer logs Each line has time, level, and msg. A line emitted inside a span also has trace_id and span_id.
Which message was not committed? Kibana Discover msg: "handle message". The fields include topic, partition, offset, err, and trace_id.
Did a fetch from the broker fail? Kibana Discover msg: "kafka fetch".
Did an outbox batch fail? Kibana Discover msg: "transmit batch". This is a claim error or a dead-letter write that the broker refused.
How do I connect a log to the trace? Kibana, then Grafana Explore, Tempo Filter on the trace_id from the log line in Kibana. Paste the same id into Tempo.

Kafka errors

The Kafka errors list on the Transfer console is the produce error, kept in memory by the console. It is not a broker log and not a receiver dead letter. A refused produce never reaches the receiver, so transfer_dlq_total does not move and there is no handle message line. Wrong address and broker unreachable fail before a connection, so the Kafka pod log stays quiet. The other four are answered by the broker.

QuestionWhereWhat to look at
Which produce was refused? Transfer console, Kafka errors The thrown text, the time, and the key. The same text is the red line in the send pane until the next send. The list is emptied when the console process restarts.
Why is the body too large? Kafka errors, after Kafka: message too large MESSAGE_TOO_LARGE. transfers.in allows 65536 bytes after compression. Repeated x compresses under that and is accepted.
Why is the topic missing? Kafka errors, after Kafka: unknown topic UNKNOWN_TOPIC_OR_PARTITION. Auto-create is off, so transfers.missing is not created.
Why is the topic name rejected? Kafka errors, after Kafka: invalid topic INVALID_TOPIC_EXCEPTION. The topic name is bad topic.
Why did the dial fail? Kafka errors, after Kafka: wrong address dial tcp 127.0.0.1:1 and connection refused. Nothing is listening there.
Why did the produce time out? Kafka errors, after Kafka: broker unreachable broker unreachable at 192.0.2.1:9092. That address does not route. The cluster broker can still be healthy.
Why was SASL rejected? Kafka errors, after Kafka: SASL rejected ILLEGAL_SASL_STATE. The listener is plaintext. This is not an access-control denial.
Did the broker log the refusal? kubectl -n transfer logs kafka-0 Use this for message too large, unknown topic, invalid topic, and SASL. A dial failure is only in the console list.
